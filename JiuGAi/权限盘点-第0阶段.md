盘点时间：2026-05-17

盘点范围：

- 后端：`JiuGAi/SillySpringboot/src/main/java/com/example/sillyspringboot/admin`
- 后台前端：`JiuGAi/RuoYi-Vue3-master/RuoYi-Vue3-master/src`

本阶段目标是只做盘点，不改业务逻辑。

## 1. 总览

- 扫描到后台相关接口：111 个。
- `/admin/**`、`/system/**`、`/getInfo`、`/getRouters`、`/logout`、`/unlockscreen` 会进入后台 JWT 拦截器。
- `/login`、`/captchaImage`、`/favicon.ico`、`/error` 被排除。
- 业务后台接口基本都有类级或方法级 `@AdminPermitted`。
- 没有业务权限注解的 9 个接口集中在认证、运行状态兼容接口，未发现普通业务 Controller 完全裸露。

## 5. 前端按钮权限

当前 `v-hasPermi` 只出现在管理员账号和管理员角色两个页面。

| 页面 | 按钮/动作 | 权限 |
| --- | --- | --- |
| 管理员账号 | 新增管理员 | `system:admin-user:edit` |
| 管理员账号 | 编辑/查看入口 | `system:admin-user:view` |
| 管理员账号 | 删除 | `system:admin-user:edit` |
| 管理员账号 | 重置密码 | `system:admin-user:edit` |
| 管理员角色 | 新增角色 | `system:admin-role:edit` |
| 管理员角色 | 启用/停用开关 | `system:admin-role:edit` |
| 管理员角色 | 编辑/查看入口 | `system:admin-role:view` |
| 管理员角色 | 删除 | `system:admin-role:edit` |

结论：大量业务页面目前主要依赖路由权限和后端接口权限，页面内的新增、编辑、删除、导入、清理等按钮没有形成统一的前端按钮级权限覆盖。这不一定造成越权，因为后端会拦，但会造成“看得到、点了才报没权限”的体验问题。

## 9. 初步问题清单

1. `finance` 角色存在模板和数据库实际权限不一致。
   - 代码模板包含 `commerce:payment:view`、`commerce:payment:edit`。
   - 当前数据库 `finance` 角色缺少这两个支付渠道权限。
   - 原因倾向于：内置角色创建后，后续代码模板更新不会自动同步已有角色权限。

2. 业务页面按钮级权限覆盖不足。
   - 当前只有管理员账号、管理员角色页面用了 `v-hasPermi`。
   - 其他业务页面靠路由和后端兜底，安全上有后端保护，但操作体验会不顺。

3. `SystemNoticeController` 的 `markRead`、`markReadAll` 是 POST，但使用 `system:notice:view`。
   - 如果这是“标记本人已读”，这个权限可以接受。
   - 如果以后扩展成管理全局公告阅读状态，需要拆出独立动作权限。

4. `/noise/dashboard/state` 未进入后台拦截器，也没有权限注解。
   - 当前返回内容很少，风险不高。
   - 但它是裸接口，后续需要确认是否仍要保留公开访问。

5. 权限颗粒度偏粗。
   - 如 `content:character:edit` 同时覆盖新增、编辑、删除、导入、清缓存。
   - 如 `commerce:entitlement:edit` 同时覆盖权益、运行设置、图片生成设置、TTS 模板上传/删除。
   - 这符合老系统简单管理方式，但不利于精细授权和风险分级。

6. 没有权限变更日志。
   - 当前能看到角色权限是什么，但不能追踪谁在什么时候改过。

## 10. 第 0 阶段结论

当前权限系统不是裸奔，后端接口覆盖基本完整；真正过时的问题集中在三处：

- 权限目录不可结构化管理。
- 前端按钮权限覆盖很少，操作体验差。
- 角色模板和数据库实际角色会漂移，缺少权限变更日志。

下一阶段建议先做“结构化权限目录 + 校验”，但必须保持旧权限 key 不变，避免已有角色失效。
