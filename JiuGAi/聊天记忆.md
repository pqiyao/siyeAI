# 聊天记忆能力改造方案 v1

本文档用于说明当前系统聊天记忆能力的问题、目标、推荐方案、数据结构、接口设计、开发步骤和验收标准。

结论先写清楚：当前系统聊天效果好，是因为聊天主链路已经走 SillyTavern 的角色卡、历史消息、世界书和 runtime prompt 构建；但当前长期记忆能力还没有真正进入 SillyTavern 的生成链路。v1 最推荐的方案不是 SpringBoot 自己重写 prompt 拼接，也不是把所有事情直接丢给 ST，而是：

```text
SpringBoot 继续作为会话事实源和记忆资产管理层
SpringBoot 从业务数据库消息中提炼长期记忆
SpringBoot 将长期记忆同步成 ST 可识别的 worldinfo / lorebook
聊天生成时继续走 ST runtime-chat/build 和 runtime-chat/generate
ST 在生成前通过 lorebook engine 按规则触发并注入记忆
```

也就是：

```text
记忆内容归 SpringBoot 管
记忆注入归 ST 管
```

这样最符合当前项目结构，也最容易得到接近 ST 的长期记忆体验。

### 1.5 当前最大问题

当前记忆只停留在：

```text
SpringBoot DB 里有摘要
H5 页面上能看到摘要
用户可以手动刷新摘要
```

但它没有真正进入：

```text
ST runtime-chat/build
ST lorebook-engine
ST prompt messages
模型生成上下文
```

因此当前记忆对模型回复的影响很弱，甚至在普通聊天链路里可能完全没有影响。

这就是用户端会觉得：

```text
短期聊天味道像 ST
长期关系、称呼、约定、事件延续不像 ST
```

根因不是 ST 不行，而是当前 SpringBoot 生成的记忆没有同步成 ST 能识别和注入的 memory source。

## 2. 改造目标

### 2.1 总目标

让长期记忆真正参与 ST 生成链路，提高用户端角色聊天体验。

具体目标：

```text
角色能记住用户称呼
角色能记住双方关系状态
角色能记住长期约定
角色能记住重要剧情节点
角色能在合适语境自然调用记忆
普通寒暄不会污染长期记忆
旧记忆和新记忆冲突时能被覆盖
记忆通过 ST worldinfo/lorebook 机制进入 prompt
```

### 2.2 v1 推荐方案

v1 推荐实现：

```text
Dynamic Memory Worldbook
```

也就是：

```text
每个 conversation 维护一份动态 memory worldbook
SpringBoot 从 app_message 中提炼长期记忆 entry
SpringBoot 调 ST /api/worldinfo/edit 写入 ST worldinfo 文件
SpringBoot 在聊天生成前把该 worldbook 文件名加入 worldNames
ST runtime-chat/build 通过 buildLorebookBlocks 按关键词/常驻/预算注入记忆
```

### 2.3 不推荐 v1 优先做 vector memory 的原因

Vector memory 上限高，但不适合作为 v1 的第一主方案。

原因：

```text
1. 当前项目已经天然走 ST worldinfo/lorebook 链路，dynamic worldbook 改造成本更低。
2. 角色扮演最重要的核心记忆是稳定事实，而不是模糊召回。
3. vector memory 依赖 embedding、chunk、召回阈值、去重和注入策略，调不好容易错记。
4. 错误召回比不记得更伤用户体验。
5. 当前 SpringBoot 的 vector 接口只是 stub，还没有实际接通 ST vector store。
```

当前 stub 位置：

```text
C:\Users\yao\Desktop\AiSillyTavern\JiuGAi\SillySpringboot\src\main\java\com\example\sillyspringboot\integration\sillytavern\DefaultStAdapter.java
```

现有方法：

```java
queryMemoryVectors(...)
upsertMemoryVectors(...)
```

这两个目前只是预留，未真正实现。

### 2.4 最终路线

推荐路线：

```text
v1: dynamic memory worldbook
v2: memory entry 管理后台和用户侧可视状态
v3: vector memory 作为远距离细节召回补充
最终: stable lorebook memory + vector retrieval memory 混合
```

### 3.3 为什么要按 conversation 生成 memory worldbook

不能做全局共享 worldbook。

原因：

```text
1. 每个用户和角色的关系不同。
2. 游客、登录用户、不同 clientUid 需要隔离。
3. 同一个角色和不同用户聊天，长期记忆不能串。
4. 删除会话、重开会话时需要清理或重建记忆。
5. ST 的 worldinfo 文件本身是用户目录内资源，但业务隔离仍应由 SpringBoot 控制。
```

推荐 worldbook 命名：

```text
jg_memory_conv_{conversationId}
```

示例：

```text
jg_memory_conv_12345
```

如果担心 conversationId 暴露，可以加 hash：

```text
jg_memory_conv_{conversationId}_{shortHash}
```

## 4. 需求说明

### 4.1 功能需求

#### FR-1 记忆提炼

系统应能从一个会话的近期消息中提炼长期记忆。

输入：

```text
conversationId
最近 N 条 app_message
已有 memory entries
角色名、用户显示名
```

输出：

```text
新增记忆 entry
更新记忆 entry
禁用过期/冲突 entry
summaryPreview
factsCount
```

#### FR-2 记忆分类

每条记忆必须有类型。

推荐类型：

| 类型 | 含义 | 示例 |
|---|---|---|
| identity | 用户身份、昵称、称呼 | 用户希望被称呼为“哥哥” |
| relationship | 关系状态 | 用户和角色已经确认恋人关系 |
| preference | 用户偏好 | 用户喜欢温柔、慢节奏的陪伴 |
| promise | 承诺、约定 | 角色答应明天提醒用户复习 |
| event | 重要事件 | 用户提到明天有考试 |
| setting | 角色扮演世界设定 | 两人住在同一间公寓 |
| boundary | 禁忌、边界 | 用户不希望被叫某个称呼 |

#### FR-3 记忆重要性

每条记忆应有优先级。

建议：

```text
200: 核心身份、称呼、关系、边界
160: 长期偏好、重要承诺
120: 重要事件、剧情节点
80: 普通事实
40: 低价值临时信息
```

#### FR-4 记忆触发词

每条非常驻记忆必须有关键词。

关键词要求：

```text
1. 2 到 8 个关键词为宜。
2. 包含用户原话中的关键称呼、地点、人物、事件。
3. 包含少量同义词。
4. 不要使用过泛关键词，如“你”“我”“今天”“聊天”。
5. 中文关键词可以不强制 whole word。
```

#### FR-5 常驻记忆

只有非常核心的记忆允许常驻。

适合常驻：

```text
用户昵称
用户希望角色使用的称呼
明确关系状态
用户明确表达的边界/禁忌
当前角色扮演中的核心世界设定
```

不适合常驻：

```text
普通事件
一次性情绪
短期话题
模型回复风格
普通问候
```

#### FR-6 同步到 ST worldinfo

系统必须把启用状态的 memory entries 同步成 ST worldinfo 文件。

ST 接口：

```http
POST /api/worldinfo/edit
```

请求体格式由当前 ST 源码确认：

```json
{
  "name": "jg_memory_conv_12345",
  "data": {
    "entries": {
      "memory_1": {
        "key": ["哥哥", "称呼"],
        "content": "Long-term memory: 用户希望角色称呼他为哥哥。角色应自然延续这个称呼，但不要每句话都重复。",
        "enabled": true,
        "constant": true,
        "selective": false,
        "position": 0,
        "priority": 200
      }
    }
  }
}
```

当前 ST `/api/worldinfo/edit` 只要求：

```text
request.body.name 存在
request.body.data.entries 存在
```

然后写入：

```text
用户 worlds 目录下的 {name}.json
```

#### FR-7 聊天生成时自动附加 memory worldbook

系统在调用 ST 生成前，应将该 conversation 的 memory worldbook 名称加入 `worldNames`。

如果原本已有世界书：

```text
["角色世界书A", "角色世界书B"]
```

附加后：

```text
["角色世界书A", "角色世界书B", "jg_memory_conv_12345"]
```

注意：

```text
不要覆盖原 worldNames
不要重复添加同一个 memory worldbook
如果该会话没有任何 enabled memory entry，可以不添加
如果 ST worldbook 同步失败，可以降级为不添加，但要记录日志和状态
```

#### FR-8 自动刷新

系统应支持自动刷新记忆。

建议规则：

```text
1. 可见消息数距上次刷新新增 >= 20 条。
2. 距离上次刷新 >= 30 分钟。
3. 会话少于 6 条可见消息时不自动生成长期记忆。
4. 生成成功后异步刷新，不能阻塞用户当前回复。
5. 手动点击“记忆”按钮时可以同步等待结果。
```

#### FR-9 手动刷新

H5 当前已经有“记忆”按钮。

点击后应执行：

```text
刷新 memory entries
同步 ST memory worldbook
返回 memory 状态
刷新聊天页记忆展示
```

#### FR-10 清理

删除会话或重开会话时，应清理：

```text
app_conversation_memory
app_conversation_memory_entry
ST worldinfo jg_memory_conv_{conversationId}
```

如果 ST 删除失败，至少要在 SpringBoot 侧标记该 worldbook 不再附加。

## 5. 非功能需求

### 5.1 稳定性

长期记忆必须稳定，不能每轮抖动。

要求：

```text
1. 不因一次普通聊天反复改写核心关系。
2. 不因模型误读生成错误事实。
3. 冲突覆盖必须偏向用户最近明确表达。
4. ST 同步失败不能影响主聊天可用性。
```

### 5.2 隔离性

记忆必须按用户和会话隔离。

要求：

```text
1. 不同 clientUid 不串记忆。
2. 不同 conversationId 不串记忆。
3. 同一角色不同用户不共享关系记忆。
4. 用户删除会话后，不再注入旧会话记忆。
```

### 5.3 可观测性

必须能排查“为什么角色记得/不记得”。

建议记录：

```text
memory refresh traceId
生成了多少 entries
禁用了多少 entries
同步到哪个 ST worldbook
本轮 worldNames 最终列表
ST buildRuntimeMessages 返回的 system message 是否包含 memory content
lorebook debug activatedCount / triggeredKeys
```

### 5.4 性能

记忆刷新不能影响主聊天响应。

要求：

```text
1. 普通聊天不等待自动记忆刷新。
2. 手动刷新可以等待，但需要超时。
3. ST worldinfo/edit 失败需要快速返回错误或降级。
4. memory worldbook entry 数量需要限制。
```

建议限制：

```text
每会话 enabled entries <= 80
常驻 entries <= 12
单条 content <= 300 中文字符
单条 keywords <= 8
worldbook 总 content <= 12000 字符
```

## 8. 记忆提炼设计

### 8.1 输入消息范围

建议每次读取最近 160 条可见消息。

当前代码已有类似逻辑：

```text
AppConversationMemoryService.refreshRollupFromMessages(conversationId)
messageMapper.listRecentByConversationAsc(conversationId, 160)
```

过滤规则：

```text
排除 FAILED
排除 DELETED
assistant 只使用 SUCCESS / STOPPED
只使用 user / assistant
排除空 content
```

### 8.2 LLM 输出结构

将当前 `ConversationMemoryLlmService.tryLlmRollup` 从“一行 summary”升级为“结构化 JSON”。

推荐输出：

```json
{
  "summaryPreview": "用户希望被称呼为哥哥，两人与角色已建立亲密关系，并约定明天继续复习话题。",
  "entries": [
    {
      "entryKey": "identity_user_call_gege",
      "type": "identity",
      "title": "用户称呼偏好",
      "content": "用户希望角色称呼他为哥哥。角色应自然延续这个称呼，但不要每句话都重复。",
      "keywords": ["哥哥", "称呼", "叫我"],
      "secondaryKeywords": [],
      "priority": 200,
      "constant": true,
      "position": "before_char",
      "confidence": 0.95,
      "action": "upsert"
    }
  ],
  "disableEntryKeys": []
}
```

### 8.3 LLM 提示词要求

记忆提炼 prompt 应明确：

```text
你是角色聊天应用的长期记忆提炼器。
只提炼会影响后续角色扮演体验的长期事实。
不要记录普通寒暄、重复语气、无意义回复。
不要记录模型自己的措辞偏好。
不要编造对话中没有出现的事实。
如果用户明确更改称呼、关系、偏好，更新旧记忆。
如果新对话否定旧记忆，输出 disableEntryKeys。
输出严格 JSON，不要 markdown。
content 用中文，简洁，给后续模型阅读。
keywords 必须来自对话关键实体或自然同义词，不要太泛。
constant 只能给身份、称呼、关系、边界、核心设定。
```

### 8.4 entryKey 生成策略

entryKey 要稳定，避免每次刷新生成一堆重复记忆。

推荐：

```text
type + normalized primary concept
```

示例：

```text
identity_user_call_gege
relationship_lovers
preference_soft_tone
event_exam_tomorrow
boundary_no_old_nickname
```

如果 LLM 输出 entryKey 不稳定，SpringBoot 可二次归一化：

```text
memory_type + title/content hash
```

### 8.5 去重与冲突

v1 必须有基本去重。

规则：

```text
同 conversationId + entryKey 命中则 update
同 type + 高相似 title 命中则 update
新 entry 和旧 enabled entry 冲突时 disable 旧 entry
用户最近明确表达优先级最高
```

冲突示例：

```text
旧: 用户喜欢被叫哥哥
新: 用户以后不想被叫哥哥，想被叫阿曜
处理:
disable identity_user_call_gege
upsert identity_user_call_ayao
```

## 13. 自动刷新策略

### 13.1 是否需要自动刷新

需要。

原因：

```text
用户不会总是手动点“记忆”
长期关系和称呼需要及时沉淀
否则用户聊了很多，模型仍然不稳定
```

### 13.2 触发条件

推荐：

```text
conversation 可见消息数 >= 6
距离上次刷新新增可见消息数 >= 20
距离上次刷新时间 >= 30 分钟
最近一次生成成功
当前没有同 conversation 的刷新任务运行中
```

### 13.3 执行方式

推荐后台异步：

```text
Chat generation done
  -> memoryRefreshScheduler.scheduleIfNeeded(conversationId)
  -> executor 异步执行
```

不要阻塞 SSE done。

### 13.4 失败处理

```text
LLM 提炼失败：保留旧 entries，记录 syncStatus=FAILED 或 extractStatus=FAILED
ST worldinfo/edit 失败：保留 DB entries，syncStatus=FAILED，下轮重试
JSON 解析失败：不更新 entries，记录错误
```

```text
6. 调 /api/runtime/chat/build 验证 messages 中出现 Long-term memory 内容。
```

验收：

```text

隔多轮聊天后角色仍自然使用称呼

```

### Phase 3：自动刷新

目标：

```text
用户不手动点击，系统也能周期性整理记忆。
```

任务：

```text
1. 新增 MemoryRefreshScheduler。
2. 生成成功后 scheduleIfNeeded。
3. 根据 message count 和时间判断是否刷新。

```

验收：

```text

不影响 SSE done 速度。
失败不影响主聊天。
```

### Phase 4：清理和后台观测

目标：

```text
记忆不会脏、不会串、能排查。
```

任务：

```text
1. 删除会话时删除 memory entries。
2. 重开会话时删除 memory entries 和 ST worldbook。
3. 后台增加 memory 状态查看。
4. debug 接口增加当前 worldNames 和 memory worldbook 状态。
```

## 17. 风险和注意事项

### 17.1 最大风险：错误记忆

错误记忆比没有记忆更伤体验。

控制方法：

```text
1. 只记录长期事实。
2. 低 confidence 不启用。
3. 冲突时保留最新用户明确表达。
4. 允许后台禁用或编辑记忆。
```

### 17.2 最大体验风险：过度注入

如果常驻记忆太多，角色会反复提旧事。

控制方法：

```text
1. 常驻 entries <= 12。
2. 普通事件必须关键词触发。
3. content 文案要求“自然延续，不要每次重复”。
4. 设置 char/token budget。
```

### 17.3 ST worldbook 同步风险

ST 不可用或 worldinfo/edit 失败时，不能影响主聊天。

控制方法：

```text
1. 手动刷新可以返回失败。
2. 自动刷新只记录失败，下次重试。
3. 聊天生成时如果 memory sync_status 不成功，可以跳过 memory worldbook。
```

### 17.4 数据膨胀

长期聊天会产生很多 entry。

控制方法：

```text
1. 每会话 enabled entries 限制。
2. 低 priority 旧 entry 归档。
3. 相似 entry 合并。
4. 删除会话时清理。
```

## 18. 为什么 v1 不直接做 summary 注入

可以做，但不推荐作为最终 v1。

summary 注入优点：

```text
开发最快
立刻看到一点效果
```

缺点：

```text
每轮硬塞，token 浪费
不按关键词触发
模型容易反复提摘要
不符合 ST 的 worldinfo/lorebook 生态
后续会越来越难调
```

因此如果要抢救体验，可以临时加一个 summary system block；但正式 v1 应以 dynamic worldbook 为主。

---

## 19. 为什么 v1 不优先做 vector memory

Vector memory 适合后续做远距离细节召回。

但 v1 的核心是让角色稳定记住：

```text
称呼
关系
偏好
承诺
核心设定
```

这些更适合结构化 lorebook，而不是向量召回。

Vector memory 的问题：

```text
1. 召回可能不稳定。
2. embedding 质量影响大。
3. chunk 切不好会污染。
4. 注入错记忆会严重破坏角色体验。
5. 当前 SpringBoot 仅有 vector stub，未真正实现。
```

推荐后续 v3 做：

```text
dynamic lorebook 负责稳定事实
vector memory 负责远距离事件细节召回
```

## 20. 最终推荐实施顺序

推荐顺序：

```text
1. 先做 dynamic memory worldbook 手动刷新闭环。
2. 再把 memory worldbook 自动挂进 AppChatService 的 worldNames。
3. 再做自动刷新。
4. 再做后台查看和编辑。
5. 最后补 vector memory。
```

最小可用版本：

```text
新增 memory_entry 表
结构化提炼 entries
ST /api/worldinfo/edit 同步
生成前附加 jg_memory_conv_xxx 到 worldNames
```

只要这四件事完成，聊天长期记忆体验就会明显改善。

## 22. 关键事实依据

## 23. 为什么不能直接全交给 ST

这个问题非常关键，因为目标是尽量接近 ST 的聊天记忆体验。

### 23.1 原版 ST 链路

原版 ST 的使用方式是：

```text
用户
  -> ST 前端
  -> ST 后端
  -> ST chat 文件 / 角色卡 / 世界书 / 向量能力
  -> prompt
  -> 模型
```

在这个链路里，ST 自己知道：

```text
当前用户是谁
当前角色是谁
当前 chat 文件是哪一个
当前启用了哪些世界书
当前聊天历史是什么
当前世界书设置是什么
```

### 23.2 当前商业 H5 链路

当前项目的用户实际链路是：

```text
用户
  -> H5
  -> SpringBoot
  -> ST
  -> 模型
```

SpringBoot 才知道：

```text
clientUid
登录用户 / 游客用户
会员额度
VIP 权限
conversationId
app_message 事实消息
会话是否删除/归档/重开
当前用户是否能访问这个角色
当前会话绑定哪个 ST chat 文件
```

ST 并不知道 H5 业务层的这些概念。

因此，如果“完全直接交给 ST”，会遇到这些问题：

```text
1. ST 不知道某条记忆属于哪个 H5 用户。
2. ST 不知道某条记忆属于哪个 conversationId。
3. 同一个角色不同用户的记忆可能串。
4. 用户删除或重开会话后，ST 侧旧记忆可能没有被清理。
5. 会员/游客/权限隔离无法由 ST 原生前端逻辑保证。
6. H5 的消息事实源在 app_message，不完全等于 ST chat 文件。
```

### 23.3 正确分工

正确方案不是“绕过 SpringBoot 直接让 ST 自己记”，而是：

```text
SpringBoot 负责业务隔离和记忆事实
ST 负责 lorebook 触发和 prompt 注入
```

这才符合当前架构。

也就是说：

```text
记忆生成、归属、刷新、禁用、删除：SpringBoot 管
记忆注入、关键词触发、位置、优先级、预算：ST 管
```

### 23.4 这个方案是不是走 ST

是。

但要准确描述：

```text
不是走 ST 原版前端 UI 的记忆管理
是走 ST 后端 worldinfo/lorebook 注入机制
```

生成时链路是：

```text
AppChatService
  -> worldNames = 原世界书 + jg_memory_conv_xxx
  -> StClient.streamRuntimeChatGenerate
  -> ST /api/runtime/chat/generate
  -> runtime-chat.js
  -> buildLorebookBlocks(...)
  -> buildRuntimeMessages(...)
  -> 模型
```

所以从“模型最终如何看到记忆”的角度看，这是 ST lorebook 方式。

从“记忆如何产生和隔离”的角度看，这是 SpringBoot 业务增强。

## 24. 预期效果边界

### 24.1 v1 能达到什么效果

v1 dynamic memory worldbook 主要提升稳定长期事实。

预期效果：

| 能力 | v1 预期效果 | 原因 |
|---|---:|---|
| 用户称呼记忆 | 高 | 适合常驻 entry，高优先级，稳定注入 |
| 关系状态记忆 | 高 | 适合常驻或高优先级触发 |
| 边界/禁忌记忆 | 高 | 适合常驻，且应优先级最高 |
| 核心设定记忆 | 高 | 适合 worldbook 机制 |
| 用户偏好记忆 | 中高 | 适合关键词触发和部分常驻 |
| 承诺/短期事件 | 中高 | 依赖关键词触发，如“明天”“考试”“复习” |
| 很久以前的零碎细节 | 中 | 需要后续 vector memory 才会更强 |
| 模糊语义回忆 | 中低 | lorebook 更适合关键词和结构化事实 |

### 24.2 和 ST 原生体验的关系

不能承诺“100% 等同 ST 原版前端体验”。

更准确的目标是：

```text
在生成时使用 ST lorebook/worldinfo 机制
在 H5 商业架构下实现多用户隔离
在称呼、关系、边界、核心设定上接近 ST 世界书效果
```

按能力估算：

```text
称呼 / 关系 / 边界 / 核心设定：接近 ST 世界书体验的 80% - 90%
承诺 / 短期事件：约 70% - 85%
远古零碎细节 / 模糊回忆：约 40% - 60%，后续需 vector memory 补强
```

这些数字不是代码保证值，而是按机制给出的工程预期。真实效果还取决于：

```text
记忆提炼 prompt 质量
entry 清洗规则
关键词质量
常驻数量控制
worldbook 同步稳定性
模型本身遵循上下文的能力
```

### 24.3 v1 不解决什么

v1 不负责解决：

```text
全量聊天历史无损回忆
跨会话共享用户画像
跨角色共享长期用户偏好
向量检索式远距离记忆
用户手动编辑所有记忆的完整后台
ST 前端原生世界书 UI 复刻
```

这些可以作为后续版本。

## 27. 上线、降级与回滚

### 27.1 功能开关

建议增加配置：

```yaml
app:
  memory:
    dynamic-worldbook-enabled: true
    auto-refresh-enabled: true
    attach-to-generate-enabled: true
    attach-to-continue-enabled: true
    attach-to-regenerate-enabled: true
    attach-to-suggestions-enabled: true
```

用途：

```text
可以单独关闭自动刷新
可以单独关闭生成时附加
可以保留手动刷新调试
上线初期便于灰度
```

### 27.2 降级策略

手动刷新失败：

```text
返回错误给 H5。
不修改旧 entries。
不删除旧 worldbook。
```

自动刷新失败：

```text
只记录 syncStatus/syncError。
不影响当前聊天。
下次满足条件继续重试。
```

生成前附加失败：

```text
跳过 memory worldbook。
继续使用原 worldNames 生成。
记录 warn 日志。
```

ST 不可用：

```text
不阻塞主聊天已有降级逻辑。
memory sync 标记 FAILED。
```

### 27.3 回滚策略

如果上线后发现记忆污染，可以快速回滚：

```text
1. 关闭 attach-to-generate-enabled。
2. 保留 DB entries，停止注入。
3. 关闭 auto-refresh-enabled。
4. 排查 entry 清洗和冲突策略。
5. 修复后重新开启。
```

如果发现 ST worldbook 脏数据：

```text
1. 后台批量删除 jg_memory_conv_*。
2. 清空 app_conversation_memory.sync_status。
3. 重新手动刷新指定会话。
```

## 28. 开发优先级

优先级最高：

```text
1. 多用户/多会话隔离。
2. 记忆能真正进入 ST runtime build。
3. 常驻记忆严格限制。
4. 冲突覆盖。
5. 删除/重开清理。
```

可以稍后做：

```text
1. 后台可视化编辑。
2. vector memory。
3. 跨会话用户画像。
4. 更复杂的记忆评分系统。
```

不要先做：

```text
1. 全局共享记忆。
2. 所有历史无差别塞入 worldbook。
3. 每轮同步 ST worldbook。
4. 不经清洗直接信任 LLM 输出。
5. 让前端传 memory worldbook 名称。
```

## 29. 最终确认

本方案的最终形态是：

```text
多用户隔离版 ST lorebook 记忆
```

准确含义：

```text
不是摘要记忆。
不是全局角色记忆。
不是 SpringBoot 自己拼一坨 system prompt。
不是完全照搬 ST 前端世界书管理。
```

而是：

```text
SpringBoot 从业务消息事实中提炼结构化长期记忆。
SpringBoot 按 conversationId 维护独立 memory worldbook。
SpringBoot 将该 worldbook 写入 ST worldinfo。
SpringBoot 生成前只把当前会话 worldbook 加入 worldNames。
ST 使用现有 lorebook-engine 在生成前触发和注入记忆。
```

这条路线能最大化复用 ST 当前有效的聊天上下文能力，同时保留商业 H5 必须具备的用户隔离、会话隔离、删除清理和权限控制。
